# CI, выпуск и откат

**Действующий порядок.** FULL вызывает `bash scripts/quality-check.sh` без аргументов. FAST применяется в итерациях. CI smoke запускается через `SMOKE_MODE=ci bash scripts/smoke-check.sh` с отдельным проектом ai-mp-cismoke, собственной сетью и томом. В Phase A сохраняются independent review, mutants, scoped/full, доказательства на финальном SHA, правила их повторного использования и явного waiver. Деплой выполняется после merge.

**Контракт задачи 1.** В приватном продукте запускать на открытие PR и каждое обновление его ветки, checkout именно head SHA, без двойного push + pull_request прогона. Ввести именованный обязательный итог, который требует успеха FULL и smoke. Записывать SHA, run ID, режим full, число собранных/пройденных/пропущенных тестов, журналы и длительность. Отменённый или пропущенный job не даёт GO. Защитить выбор SHA от подмены merge ref. Согласовать правило слияния и проверку итогового merge при расхождении дерева. Для переиспользования соблюдать существующее исключение на документальный diff и приложить diff/evidence в release.md.

Использовать штатный quality script, PostgreSQL service, TEST_DATABASE_URL для одноразовой БД, значения FF_* из .env.example; synthetic fixtures, pinned dependencies, браузер для tests/e2e_spa. Сохранить format/lint/guardrail/typecheck/frontend, все pytest включая интеграционные и src/*/tests, --dist loadfile и tests/support/db_isolation.py. Проверить независимость БД и smoke сетей. Если matrix потребует доработки entrypoint, объединить результаты всех shard и доказать полноту сравнением node IDs с нешардированным FULL. Проверить p95 от push до результата и стоимость; цель 20–25 минут. Продовые ключи отсутствуют у PR jobs, права read-only; публикация образов из доверенного workflow. На финальном SHA зелёный CI засчитывать как FULL после согласованного изменения продуктового протокола CLAUDE.md §§4/6/11 и release-engineer; при недоступности CI — локальный FULL с evidence. Эта поставка документирует контракт.

**Изменение релиза.** Нынешний DEPLOY.md B требует SemVer до выкладки и включает сборку на сервере. Новый порядок требует отдельного staging-пути по SHA/digest до release tag. До переключения изменить и проверить этот контракт в продукте. Текущий whereami.sh верифицирует IP из env среди адресов хоста. При одинаковом IP двух окружений нужен независимый от env барьер: разные системные deploy identities/каталоги и разрешённые Compose project, DB/volume и service account. Тест подставляет prod env в staging и наоборот; операция обязана завершиться отказом до соединения с БД.

1. После merge собрать образы единожды, записать SHA → digest каждого компонента и provenance. Проверить миграции и совместимость предыдущего приложения со схемой.
2. Выложить точные digest на persistent staging. Проверить миграции, UI, API, sync и smoke. Release-инженер подписывает отчёт с SHA/digests.
3. Создать защищённый release tag только после staging GO. Проверить доступность rulesets/защиты тегов в приватном аккаунте: API вернул ограничение тарифа. Перед внедрением согласовать доступный механизм и расходы. Отрицательные испытания: произвольный тег, подменённый digest, отсутствующий отчёт и неверное окружение блокируют deploy.
4. Ограниченный deploy-сервис сверяет tag, SHA, manifest, staging GO. Prod читает те же digest. После развёртывания проверить health, smoke, p95, ошибки и sync. При сбое остановить продвижение и вернуть предыдущий manifest. Схему восстанавливать по отдельному forward-recovery плану; restore работающей БД требует решения владельца.
